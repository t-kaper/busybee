# Оставшиеся риски Runtime

Этот документ фиксирует не общую архитектуру, а именно те места, где текущий
runtime BusyBee ещё не идеален после упрощения системы и удаления command layer.

---

## 1. Разрыв между БД и `NodeRunQueue`

Сейчас runtime использует два уровня состояния:

- статус `pipeline_node_run` в БД
- локальную `NodeRunQueue` в памяти процесса

Главный риск:

- `Dispatcher` уже перевёл run в `queued`
- но воркер ещё не получил `node_run_id` из памяти
- при сбое между этими шагами можно получить `queued`, который не исполняется

Почему это важно:

- `queued` выглядит как "задача уже передана на исполнение"
- но у неё может не быть фактического владельца
- такие run приходится лечить recovery-механикой

Что с этим делать позже:

- либо перейти на `DB-only` схему без in-memory очереди
- либо ввести lease/claim model для `queued/claimed`

---

## 2. `pipeline_run` зависит от текущего DAG, а не от snapshot

`UpdatePipelineRunStatus` сравнивает количество узлов run с текущим содержимым
`busybee_pipeline_node`.

Главный риск:

- `pipeline_run` уже запущен
- definition pipeline потом изменили
- старый run начинает сравниваться с новым DAG

Это может привести к тому, что:

- `pipeline_run` не закроется
- метрики и UI начнут видеть "вечный active"

Что с этим делать позже:

- хранить snapshot/version DAG на момент старта `pipeline_run`
- или запрещать изменение DAG при активных run

Что уже делается сейчас на уровне API:

- если у pipeline есть `active` run, API разрешает только `is_active -> false`
- delete pipeline запрещён, пока есть `active` run
- активация pipeline требует graph validation

---

## 3. Final state всё ещё зависит от доступности БД

После завершения процесса worker должен записать terminal-status:

- `success`
- `failed`

Сейчас код уже делает retry записи, но если БД недоступна слишком долго,
теоретически возможен сценарий:

- процесс уже завершился
- а в БД run всё ещё `running`

Почему это важно:

- `pipeline_run` может не закрыться вовремя
- monitoring видит "живой" run без живого процесса

Что с этим делать позже:

- отдельный reconciler для stale `running`
- или более жёсткая модель владения run через lease/heartbeat

---

## 4. Graceful shutdown не гарантирует полный drain очереди

При штатной остановке процесса:

- общий `ctx` отменяется
- локальная очередь закрывается
- часть `queued` run может остаться недоисполненной до следующего старта

Это не критично для модели "recovery on boot", но важно понимать:

- graceful shutdown сейчас best effort
- он не гарантирует, что всё уже поставленное в очередь будет доработано до конца

Что с этим делать позже:

- делать полный drain
- или отказаться от локальной очереди как от критичного runtime-слоя

---

## 5. Текущая модель предполагает один активный runtime на БД

В `main.go` уже есть advisory lock, и это правильно.

Это означает:

- текущая реализация рассчитана на один активный engine process на одну БД
- multi-instance orchestration сейчас не является целевой моделью

Почему это важно:

- многие recovery-механизмы проще именно в single-runtime режиме
- при переходе к нескольким runtime потребуется redesign claim/lease semantics
